## 4. 四目标评估（Phase 3）

### A. 一次完整对话是否可以被追踪？—— **部分满足（约 40%）**

- ✅ 有：conversation_history（per-user 落盘）、RuntimePipeline 的 trace（lifecycle_id 贯穿 3 阶段）、audit 的 message.received/responded、memory.created。
- ❌ 缺：trace 不注入审计（无 trace_id 关联）；orchestrator 直连路径与 main.py 路径零 trace；RuntimeCore 17 阶段内部无任何轨迹；trace 阶段粒度只有 3 个。
- **结论**：入口到出口的"线"在 pipeline 路径勉强存在，但**审计、事件、轨迹三系统互不关联**，无法按 request 维度重建一次完整对话的读写历史。

### B. 一次人格变化是否可以解释来源？—— **部分满足（约 65%）**

- ✅ 有：self_model 治理链硬契约（apply_change_proposal 只能来自 AUTO_APPLY 或已批准 proposal）+ before/after 审计（self_model.write）；growth proposal 带 evidence_ids/source_event_id；personality_state.json 带 applied_proposal_ids。
- ❌ 缺：personality_state.json 由 RuntimeCore 直接写（不经治理链）；personality_growth_history 由 narrative adapter 写（与 growth_history 双记录）；legacy relationship.bypass_write 路径仍在；growth_history 169 条无 user_id 溯源（已归档评估见 P2.2 报告）。
- **结论**：self_model 单点解释性好；但 personality 全域的"事件→理解→评估→proposal→审核→应用"闭环**尚未覆盖所有变更来源**，存在两条旁路写入。

### C. 新增视觉/语音/身体模块是否需要大量修改核心代码？—— **需要中等偏大修改（约 30% 就绪）**

- ✅ 有利：adapter 抽象契约已存在（adapters/base.py 禁 import 业务模块；registry 模式）；perception/ 包与 screen_context_manager 已有先例（Step 3.5）；canonical runtime.py 是 17 阶段可插拔设计。
- ❌ 障碍：生产主路径是 orchestrator 硬编码 15 步 + Legacy RuntimeCore；Step 3.5 是**硬编码**在 process 里的特例而非注册机制；无统一事件总线（新模态事件不知发到哪个总线）；无统一 RuntimeContext（新模态上下文无标准挂接位）。
- **结论**：加一个新模态 ≈ 在 orchestrator.process 与 RuntimePipeline 两处各插一段硬编码（现状先例：屏幕模块就是这么加的），且无法获得统一追踪/审计/事件。**规模化多模态前必须先做 RuntimeContext/EventBus 统一**，否则每个新模态都是一次核心文件手术。

### D. 未来"羽依设计委员会"是否有安全接入点？—— **有雏形（约 60%）**

- ✅ 已有：P2.1.3 Permission Gate（五扇门，身份维权限）；governance_provider（propose/review/list）+ `/api/admin/governance/{personality,memory,growth}` 端点；approval_manager / GrowthProposal 审核流；self_model 审批队列（AUTO_APPLY / APPROVAL_REQUIRED / DENY 规则）；审计 before/after。
- ❌ 缺：审批队列为**内存态**（重启丢失）；委员会 = 多角色评审（AGENTS.md §6 的 Architecture/Safety/Emotion/Growth Reviewer）尚无任何代码实体；无统一事件通知（委员会如何被唤醒？）；admin 治理端点与运行时写路径之间无统一收口（旁路直写仍在）。
- **结论**：**接入点安全（权限门+治理 provider+审计），但委员会的"多角色会话"需要新的挂接面**——推荐挂接位为 governance_provider 之上的评审会话层 + 统一事件总线通知 + 审批队列持久化。

## 5. P2.3 实施建议

> 原则（承 P2 系列）：**不重写、不加孤立模块、先收口再扩展**。P2.3 的目标是让已有能力形成闭环，而不是新建 Runtime。

### 建议 1：统一 RuntimeContext（G1，最高优先）
- 以 `lifecycle_context.RuntimeContext` 为唯一请求级上下文，`runtime_context.assemble_context` 降级为其构建器。
- 修 `relationship_repo` / `on_emotion_change` 断链：要么让上下文真实携带这两个键（打通 orchestrator 与 runtime_core 的关系仓库），要么删除死键+退役断链代码——二选一，**必须消除"看似接通实则空跑"的假闭环**。

### 建议 2：总线收敛（G2）
- 收敛到单一总线（推荐 `src/events/bus.py` 为唯一进程内发布面，其余 wrapper 逐步退役）；补 request_id 注入与历史持久化（personality_event_bus 的持久化设计可参考）。
- 接线 `register_builtin_handlers()`（audit/proposal/experience 桥），使事件→审计自动桥接成立。

### 建议 3：审计/追踪/事件三系统关联（G4）
- record_audit_log 增加 trace_id 字段，与 RuntimeTraceRecorder 的 lifecycle_id 对齐；RuntimeCore 主循环补关键阶段审计。
- 目标：一个 request_id 可同时检索 trace 记录、audit 记录、总线事件。

### 建议 4：RuntimeCore 二选一（G3，高风险，需独立审批）
- 现状 Legacy RuntimeCore 是事实权威。选项：a) 承认 legacy 为权威、冻结 canonical runtime.py（防测试假闭环继续扩散）；b) 按 Phase R3 计划切到 canonical。**本报告不推荐 P2.3 内切换**，只建议先做"权威声明 + 停写未接线代码"。

### 建议 5：relationship 收口（G5）
- 明确 `data/users/{uid}/` 仓库为唯一权威，legacy `relationship_state.json` 明确为只读镜像（P2.2 已归档其历史）；orchestrator 关系 post 链要么接上真仓库要么退役（与建议 1 联动）。

### 建议 6：情绪 decay 接线（G6）
- 在请求路径或 tick 中引入 decay 调度（一行级改动，需确认衰减参数与测试）。

### 建议 7：孤儿代码处置（G7）
- integration host、growth_loop、growth/sync、proposal_events、pipeline_server 等：**不删**，但在代码头加"未接线（unwired）"标记 + 维护 docs/architecture/wiring_status.md 台账，防止后续任务误判为活跃路径。

### 建议 8：为设计委员会预留挂接面（Phase 3-D）
- 不做实现，只做**接口冻结**：评审会话输入 = (proposal, 事件证据, 权限身份)；输出 = approve/reject/需要补充证据；通知 = 统一总线事件；持久化 = 审批队列落盘。P2.3 只把审批队列从内存改为落盘（data/approval_queue.json），委员会本体留待后续 Phase。
